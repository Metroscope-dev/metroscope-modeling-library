# MML4 — isolated component test triplet (mandatory workflow)

Trigger: "Créer les modèles tests de ce composant X", "tests unitaires X", "reverse/direct/faulty pour X".

## Contract and files
Create exactly three independent, openable Modelica files `<X>_reverse.mo`, `<X>_direct.mo`, `<X>_faulty.mo` with proper `within` scope and version evidence. **One single physical component under test** in EACH file. Other instances limited to required medium-specific sources/sinks, instrumentation (`SensorsControl`), signal interfaces (`Utilities.Interfaces`) and directly necessary thermal/electrical boundary components or balancing elements. Do not insert additional process machinery or an upstream/downstream plant. The files share an operating point, consistent component placement/scale, measurement locations and comparable interfaces. Preserve fixed icon dimensions. Always include the source ref/commit used to look up the API.

## Derive from the real API
1. Inspect the component's inheritance chain, fluid connectors, parameter connectors (`GenericReal`), physical source/sink needs, initialization fields, governing equations, fault implementation (`faulty`, fouling, leakage, efficiency loss, etc.), and reference unit tests. Prefer user's verified MML4 AirCompressor trio as the **pattern**, not as a source of guessed APIs for unrelated components.
2. Choose a realistic stand-alone boundary setup. Use plausible CCGT / REP 1300 values based on component and circuit. Sensor display units only `degC`, `barA`, `kg/s` where applicable; internal SI stays SI. Record assumptions.
3. Build a sensor-to-parameter table. Keep `sensor_function="BC"` for boundary signals, `"Calibration"` for observables used to estimate a parameter, and `"Unidentified"` for remaining observables. Keep `causality` equal to the exact actual parameter name. Use correct MML4 graphical interfaces: BC => `BoundaryCondition` in both; Calibration => `CalibrationInput` in reverse, `Observable` in direct; Unidentified => `Observable` in both. The actual target version takes precedence over generic tables. The nominal faulty model should use direct-like BC/parameter contracts unless the verified golden pattern specifies otherwise.
4. Reverse: impose independent observed values for parameter identification and leave calibrated component parameters to solve. Direct: impose calibrated parameters through their verified graphical ports and output calculated measurements; do not retain reverse calibration interface as input. Verify equation/unknown count and physical observability.
5. Faulty: use actual component failure settings, e.g. `faulty=true` and verified fault magnitude as allowed by class; ensure a deterministic realistic fault and physically interpretable output. If a class has no fault capability, never invent a field or fabricate success; document inability or supply a clearly named alternative fault-injection wrapper *only with explicit user request*.
6. Set supported sensor `P_start`, `P_0` (barA -> Pa), `T_start`, `T_0` (degC -> K), `Q_start`, `Q_0` (kg/s) and component's supported initialization parameters, from consistent local operating state. Check modifiers against actual inherited classes.
7. Graphical QA: all `connect(...)` get actual endpoint `annotation(Line(points=...))`; cluster P/T/flow sensors downstream near component, interface near corresponding sensor, parameter connectors near ports, no crossings through symbols. Absolutely **do not alter icon sizes**; translate placements only. Compare icon dimensions to same-version reference and reject resizing.
8. Check connectors' domains and flow signs, fluid properties, pressure/temperature plausibility, no double imposition (flow boundary vs component volumetric flow parameter, etc.), no floating signal connector, and basic equation balance. When tooling supports, translate and solve EACH of the three models in Dymola. Never claim simulation without running it.

## Deliverable audit
Supply three `.mo` files and short matrix: model, independent BC, imposed/identified params, output sensors, fault flags, equation balance, compile/solve status, diagram QA status. Show limitations and initialization values. Preserve user's proven-working test templates when extending/changing.
