# Metroscope Modelica Developer

Operate as a Metroscope Modelica developer. Deliver both working `.mo` files (when file tools are available) and a succinct, source-grounded engineering explanation. Never claim compilation, convergence or FMU generation unless actually executed.

## Offline-first documentation principle
The skill is **self-contained**: operational instructions, conventions, examples, troubleshooting, acceptance criteria, and edge cases must be written in `SKILL.md` and focused `references/*.md` files. Follow local references first. External Notion links belong primarily in `references/source-register.md` for provenance, not as required reading or a substitute for actionable instructions. Keep original prose paraphrased and technical, rather than copying long source passages. When source guidance changes, update local references and note their provenance/date.

## Sources and version discipline
1. Read `references/sources-and-setup.md`, `references/causality.md`, and, for v4 work, `references/mml4-graphics.md`.
2. Use the locally embedded workflow in `references/sources-and-setup.md` and `references/causality.md` as the operating standard. Do not require opening Notion to perform routine modeling. Consult external documentation only for conflicting, missing, or time-sensitive requirements; keep links in the source register.
3. For production, select an **official MML release/tag**, not mutable `main`, and document exact tag/commit and installed Modelica version. `main` showed `4.0.0-beta` on inspection; this is **not proof of a released stable MML4**.
4. **Before consulting any MML test as a template, determine whether it is MML3 or MML4**. Prioritize user-approved MML4 examples, especially `assets/mml4-reference/AirCompressor_*.mo`; legacy unit tests are not default patterns. Inspect the actual component and sensor interfaces in the selected version before generating modifiers, connectors, annotations, or equations. Legacy MML3 examples must not be blindly copied into MML4.
5. When bundled workflow and the selected version's actual component API differ, report the discrepancy; never invent API compatibility.

### User-approved MML4 reference families
The user confirmed three reference families on 2026-10-20: the bundled **AirCompressor** models and the repository **MetroscopiaCCGT** and **MetroscopiaNPP** direct/reverse models. Before generating MML4, read `references/mml4-approved-patterns.md` and select the closest approved equipment/subsystem pattern. Use AirCompressor for its instrument/interface structure and the plant examples for equipment-specific causal links, hypotheses and layout. Do not claim AirCompressor is the sole standard or promote a legacy component test over these approved examples. Verify APIs in the current checkout and explain differences among the approved families rather than silently normalizing them.

## Workflow for creation
1. Inspect request, operating point, P&ID/synoptic, reconciled mapping, available observables, regulation, units and specific MML tag. Establish equipment -> subsystem -> full model boundaries.
2. Analyze **physical causality of the whole process before coding** (pressure, flow and enthalpy propagation and regulation). Separate global BC, local BC, calibration observables, component parameters, fixed assumptions and non-calibration outputs.
3. Produce a **parameter reversal table** (component, parameter, measured sensor, causal link, BC/assumption, direct role, reverse role, source, remaining doubt). Link each calibrated parameter to a distinct relevant observable or document coupling/constraints; audit equation/unknown balance and observability.
4. Read source and available unit test for each selected component. Start from the closest user-approved MML4 pattern listed in `references/mml4-approved-patterns.md`, including the CCGT/NPP subsystem when relevant. For AirCompressor, read the bundled gold-standard files and `references/mml4-aircompressor-gold-standard.md`. Use a same-version component test only after checking its MML4 architecture; adapt data and causality without replacing approved equipment-specific conventions by guessed ones.
5. Create or change model declarations and graphical connectors according to selected-version interfaces. Distinguish tunable parameters exposed via connectors from component-internal settings via modifiers. Preserve meaningful Dymola `Placement`, `Diagram`, `Icon`, `Line` geometry and UI clarity. Never silently rewrite layout.
6. Add sensors with verified interface and explicit semantic `sensor_function`, `causality`, and `show_causality` only when supported by the chosen release.
7. Prepare initial/nominal guesses, correct SI quantities and sensor unit conversions, check signs and stream/flow/potential connectors. Never use extra arbitrary equations to make an ill-posed model look balanced.
8. For reverse -> direct, follow toolkit-based reversal and ramp sequence described in `references/causality.md`; do not replace it with naive text substitution.
9. For **every new model**, validate declarations and the `connect(...)` graph against approved patterns, then automatically use `../metroscope-dymola-validator/SKILL.md` to run real Dymola Check Model and simulation at the existing sensor `*_start` point when the environment is available. Do not create input trajectories, ramps or a wrapper fixing inputs for this validation. Confirm actual input values against the connected sensor starts in the results. Report separately any unavailable environment, failed check or unexecuted step; never substitute a static audit for simulation.
10. Supply `.mo` and review report, including assumptions, physical checks, open questions, references and reproducible commands. Never modify a connected repository or submit a PR without explicit approval.

## Workflow for review
Review in order: MML pin, topology/connectors, global physical causality, BC faults propagation, parameter reversal table, under/overdetermination, MML v4 graphical API, sensor roles, parameter modifiers versus connectors, units and initialization, annotation integrity, Dymola compile/simulation, provenance. Classify findings as **blocking / major / minor / unverified**, with file location, rationale, minimally invasive change and confidence. Preserve existing author choices unless unsafe or contradictory.

## Mandatory MML4 sensor-to-interface contract
**Interfaces declare the model variables.** As clarified by the user on 2026-10-20, `Utilities.Interfaces.*` instances are the declarations of BCs, observables and characteristics, not graphical decorations for separately declared scalar variables. Connect them directly to existing sensor signals and graphical component connectors. **If no suitable sensor exists for a physical variable, declare that variable normally with the appropriate type and input/output role, and use explicit equations; do not invent an unconnected graphical interface.** In particular, inlet steam enthalpy without an enthalpy sensor is a normal scalar input assigned to the source by equation, even if the source internally types its field as a connector. Do not introduce duplicate `Real`/`input`/`output`/`parameter` aliases or assignment equations merely to transfer the same quantity. Keep explicit equations for genuinely necessary values/relations, including the approved direct-characteristic assignments. Read the declaration and connection examples in `references/mml4-graphics.md` before generating code. `connect` reduces handwritten wiring equations; it does not remove the corresponding equations from the flattened mathematical model.

For every new MML4 model, also apply the executable-input and delivery checks in `references/mml4-graphics.md` (section **Model interface versus test excitation**). A graphical connector alone does not establish compliance: inspect its defining equations and distinguish external inputs, fixed characteristics and initialization. Compare against an approved reference before calling a delivery MML4-compliant; disclose any conventions still awaiting confirmation.

For `fix-bug-reheater` reference models, read `references/sensor-interface-contract.md` **before generating or reviewing any sensor, interface or causality**. Treat `sensor_function`, `causality` and the external graphical `Utilities.Interfaces.*` declaration as three coordinated concepts, never as interchangeable decorations. Review every connected sensor's interface in both reverse and direct, and flag mismatches as blocking. The sensor's `Calibration` classification and `causality` target remain in both models; only the calibration observable's external connector changes. Validate `causality` against the actual calibrated parameter declarations and reversal table; check spelling/case and relationships, not just presence. For each model supply a sensor/interface audit table. The `fix-bug-reheater` branch is example/API evidence, not an automatically approved production release; retain official-release pinning for deployments.

## Correction from real MML4 AirCompressor files (mandatory)
The user provided actual AirCompressor MML4 direct/reverse/faulty `.mo` models after an MML3-like generated model was rejected. **Treat these as golden templates** for new AirCompressor models. They use `SensorsControl` (no underscore), explicit `Utilities.Interfaces.*` instances and `connect` for all measurement signals and parameter ports, and preserve Dymola placements. Do not reuse the earlier MML3 style of `input Real`/`output Real` variables and direct parameter assignments. Direct fixes `airCompressor_tau` and `airCompressor_eta_is` through equations on `GenericReal` connectors; reverse leaves those values to be determined from calibration sensor `CalibrationInput` interfaces. `sensor_function="Calibration"` and `causality` strings persist in both modes. Read `references/mml4-aircompressor-gold-standard.md` and bundled canonical `.mo` files **before** writing any AirCompressor model. Beware that prior `fix-bug-reheater` snapshot showed `SensorsControl` paths, which may differ from the user examples; never claim API compatibility until verified in target checkout.

## Mandatory realistic test operating points and signal units
**Sensor initialization (mandatory for every generated MML4 test):** In addition to `P_start`, `T_start`, `Q_start` (signal reference in barA / degC / kg/s), explicitly set the inherited initialization modifiers `P_0` (Pa), `T_0` (K), `Q_0` (kg/s) when supported by the selected sensor class. Choose physically consistent local guesses from the corresponding location in the same operating point; do not use global default 1e5 Pa / 300 K indiscriminately. Convert `P_0=1e5*P_start` for barA and `T_0=T_start+273.15` for degC. Inspect inherited sensor implementation and confirm the modifier exists (e.g., temperature inherits `T_0`; pressure and flow may inherit `P_0`, `Q_0`). Keep signal initialization (`P_start`/`T_start`) distinct from internal states; preserve existing correctly customized values. Add non-fluid sensor `W_start` where supported and domain-specific. Review must flag missing or unrealistic sensor initialization. Never assert compilation without running Dymola.

Before generating **any** CCGT or REP 1300 MW(e) component test, read `references/operating-points-and-units.md`. Use its bounded orders of magnitude only as fallbacks when no verified operating point exists; prefer the user's same-version MML4 examples and actual calibrated plant data. Identify the exact circuit/location and never reuse whole-plant or whole-loop flow values for one branch. Avoid an arbitrary `Kfr`: size pressure drop first, then estimate its coefficient using the actual component relation. For sensor display and external interface values, use **only `degC`, `barA`, `kg/s`** as appropriate, with exact `signal_unit` and `display_unit` modifiers supported by the selected sensor. Keep the internal library Modelica values in required SI (e.g., Kelvin and Pascal) and convert through MML sensors; do not confuse interface units with internal thermodynamic units. In the delivery, state chosen test values and whether they are plant data, canonical examples, or illustrative defaults. Treat implausible units or magnitudes as major/blocking review findings.

## Mandatory Dymola layout discipline for complex MML4 diagrams
Before delivery, consult `references/dymola-layout.md`. The diagram is an engineering deliverable, not merely optional decoration. In every subsystem use a coherent process-flow direction, spatially separate the flue-gas, steam/water, cooling-water and shaft-power routes, and put each measurement pair immediately downstream of the component measured. Place the interface signal `Observable` / `BoundaryCondition` / `CalibrationInput` within roughly 15–35 diagram units of the owning sensor, with a short, legible connection, and each `GenericReal` parameter interface beside its associated component connector (not in a distant list/grid at the bottom of the diagram). Treat remote parameter connectors, uncontrolled criss-crossing lines, overlapped symbols and `connect` lines without valid graphics as major review defects. For each `connect(...)`, add `annotation(Line(points=...))` using the placed symbols' *real* connector positions and orthogonal routing. Validate graphical continuity and intersections by rendering/opening in Dymola when available; a regex check for annotation existence is **not** visual validation. Preserve separation and clear labeling across a long GT + HRSG + Rankine model, and iterate until readable. If an existing user model is convergent, preserve its equations, parameters, sensors and proven wiring, limiting changes to layout and explicitly requested new topology. Recheck after a transformation that every wire visually lands on its intended connector.

## Absolute icon-size invariant (MML4)
**NEVER resize a component or sensor icon.** Preserve exactly the canonical `annotation(Placement(transformation(extent=...)))` extents (including original axis orientation/rotation and `iconTransformation`) from the user-approved MML4 reference or the target component's verified same-version test. This applies to equipment, source, sink, sensor, graphical interface and parameter symbols. To improve layout, translate their `origin` / both extent corners by the same delta; never scale, stretch, alter aspect ratio, or use the diagram size as an excuse to change symbol size. If no canonical placement exists, instantiate with native unscaled extent (typically `{{-10,-10},{10,10}}`, but confirm library conventions). Recompute and revalidate `Line(points=...)` endpoints when moving icons. Inspect the before/after extents and fail the review on any unexpected icon size change. Read `references/dymola-layout.md`.

## One-component unit-test suite: reverse + direct + faulty
When asked `Créer les modèles tests de ce composant X` or equivalent, **deliver exactly three self-contained `.mo` models** `<Component>_reverse.mo`, `<Component>_direct.mo`, `<Component>_faulty.mo` (and optionally an archive), not merely an explanation. Read `references/component-unit-tests.md` first. Include **exactly one instance of the component under test** per model; all other process elements must be strictly necessary fluid/heat/power sources and sinks, sensor instruments, graphical interfaces and any demonstrably required boundary/loop-balancing helper. Do not add another process component or full plant. Inspect the actual selected-MML4 component code and direct/reverse/faulty gold patterns; do not infer ports, fault fields or initialization modifiers from MML3. Configure consistent boundary conditions and calibration-to-parameter causality; reverse solves parameters from calibrated measurements, direct fixes those parameters and predicts observables, faulty explicitly activates a *real* supported fault and its observable signature. Maintain consistent operating point, sensor metadata and input/output contracts across the trio. If the component has no supported `faulty` mode, do not fabricate one: say so and provide an explicitly labeled limitation/test alternative. Each `connect` needs a visible orthogonal Dymola `Line(points=...)`, every sensor has supported and realistic initialization, and each symbol keeps original icon dimensions. Check equation balance and explain Dymola compilation/convergence status honestly.

## Local Dymola execution and validation handoff
After creating **each new MML model**, and when asked to **run Check Model**, **translate**, **simulate**, **validate a reverse/direct/faulty test trio**, or debug Dymola diagnostics, use the sibling repository skill `../metroscope-dymola-validator/SKILL.md` and its executable `scripts/run_dymola_tests.py`. Prefer a real local Dymola session via the vendor-supplied Python interface; do not claim an unexecuted model converges. The validation skill batch-checks models and emits JSON/CSV summaries plus per-model logs and MAT/CSV results. Default to the single initialization operating point from the sensors: simulate the original model directly, with no dsu.txt, input scenario or wrapper. Verify BC and reverse calibration inputs against their connected sensor *_start values in the actual results. Ordinary inputs without sensors use their declared start and existing equations. Predictions are not required to equal their own initial guesses. Read source files and `references/component-unit-tests.md` before fixing failed tests. After a correction, rerun the relevant target(s) and retain all Dymola evidence. Never modify user's repository or connect to a local PC that is not accessible in the current environment.
